# Лицензионная политика: что можно брать в расчётный контур

Обновлено: 2026-11-04. Проверяется для каждой новой зависимости.

## Правило

| Лицензия | Можно? | Почему |
|---|---|---|
| **Apache-2.0, MIT, BSD-2/3, ISC** | ✅ да | разрешают использование, модификацию и распространение, в том числе в закрытых продуктах; требуют лишь сохранить уведомление об авторстве |
| **LGPL-2.1/3.0** | ⚠️ с осторожностью | можно, если библиотека подключается динамически и не модифицируется; при статической сборке или правках — обязательства по раскрытию |
| **GPL-2.0/3.0** | ❌ нет | производные работы должны распространяться под GPL: наш код пришлось бы открывать целиком |
| **AGPL-3.0** | ❌ **нет** | то же, что GPL, но срабатывает и при **сетевом использовании**: достаточно предоставить доступ к расчёту через API/сайт, и весь исходный код сервиса должен быть открыт по AGPL |

## Почему AGPL — стоп

AGPL отличается от GPL одним пунктом (раздел 13): если пользователи взаимодействуют с
программой **по сети**, им должен быть предложен исходный код всей программы, включая
наши модули, которые с AGPL-библиотекой связаны. Для агента, который отдаёт расчёты
через API или веб-интерфейс, это означало бы обязательство открыть весь продукт.
Покупатель/партнёр, которому нужен закрытый контур, такую зависимость не примет.

Отдельно: «просто вызвать AGPL-утилиту как отдельный процесс» — юридически серая зона
(зависит от того, признаётся ли обмен данными «единой программой»). В продукт такое
не берём; для разовой сверки вне поставки — допустимо, но результат нельзя включать
в поставляемый код.

## Как проверять новую зависимость

```bash
pip show <пакет> | grep -i license          # для установленных
grep -i "license" <репозиторий>/pyproject.toml
head -20 <репозиторий>/LICENSE
```

Затем — запись в эту таблицу. Пакет без явной лицензии считается запрещённым.
